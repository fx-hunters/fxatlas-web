## 변경 사유 (Why)

환전 플래너는 사용자가 선택한 외화 목표의 현재 상태, 다음 행동, 상황별 대체
계획과 목표 도착점 사이의 인과를 하나의 Curve에서 이해하게 해야 했다.
1차 프로토타입으로 필요한 영역과 상호작용을 검증했지만, 목표·계획·준비 구간·
회차·시나리오·설명·행동이 동시에 보여 Curve보다 카드 정보가 먼저 읽혔다.

정보를 없애지 않으면서 현재 위치 → 다음 행동 → 상황별 대체 경로 순서로
읽히게 하고, Divisa와 Curve를 결합한 브랜드 경험을 화면 중심에 두기 위해
한 장면 안에서 정보를 순차 공개하는 2차 UI/UX 구조가 필요했다.

안전·유연 비중, 회차 생성, 달성 가능성, 상황별 계획 산식과 실제 API 계약은
여전히 확정되지 않았다. 프론트엔드는 수치를 만들거나 계획을 자동 변경하지
않고, backend 형태의 fixture 응답을 표시하는 경계를 유지한다.

## 변경 내용 (What)

- `/route`에서 반복 투자형과 마감형 데모 목표를 선택하고 Curve Dive로
  진입하는 기존 흐름을 유지했다.
- 금융·계획 상태와 별도로 `orientation`, `pathReveal`, `actionFocus`,
  `explore` 공개 단계를 두어 현재 위치, Curve, 다음 행동을 순서대로 표시한다.
  최초 자동 연출은 820ms + 620ms + 1,000ms로 3초 안에 끝난다.
- 같은 세션에서 같은 목표를 다시 열면 260ms fade 뒤 Curve와 다음 행동을 바로
  표시한다. sessionStorage에는 목표별 연출 확인 여부만 저장하며 계획 값은
  저장하지 않는다.
- “처음부터 다시 보기”는 공개 연출만 다시 실행하고 적용 시나리오와 회차 기록
  상태를 보존한다.
- 목표 요약은 상단 한 줄로 압축하고 세부 목표 정보는 사용자 요청 시 펼친다.
  계획 요약은 Curve 옆 다음 행동 영역에 통합했다.
- SVG Curve를 화면 중심에 배치하고 완료·다음·예정·도착 노드를 색뿐 아니라
  체크·화살표·점·마름모 형태와 상태 문구로 구분했다. 노드는 클릭, Enter,
  Space로 선택해 해당 지점 정보만 확인할 수 있다.
- 시나리오는 사용자가 “상황이 바뀐다면?”을 선택한 뒤 나타난다. 빠른 상승,
  회차 누락, 예산 감소 세 가지를 먼저 표시하고 “전체 상황 보기”로 예상 범위와
  하락 상황을 추가한다.
- 대체 시나리오는 기존 Curve를 남긴 채 분기 Curve를 그린다. 선택 후
  “기존 계획과 비교”를 거쳐야 “이 계획 적용”이 나타나며, 확인 대화상자 승인
  전에는 적용 상태를 바꾸지 않는다.
- 준비 구간과 전체 회차는 PC drawer와 모바일 bottom sheet로 이동했다. 이유
  설명은 선택한 노드나 시나리오 맥락 안에서 열리고 간단히/자세히 mock
  프로필 전환을 유지한다.
- Action Dock은 상태별 대표 행동 하나만 강조한다. 기록·건너뛰기·이유 보기는
  보조 행동 메뉴에 두고, 모바일 내비게이션 위에 134px 높이로 고정한다.
- 기존 토큰과 `Badge`, `ProgressBar`, `Icon`, `Card`를 재사용하고
  리터럴 색상과 새 패키지를 추가하지 않았다.
- reduced motion에서는 순차 이동과 pulse를 짧은 fade로 바꾸며, live region,
  focus-visible, 키보드 조작과 Curve 대체 설명을 유지한다.

## 영향 / 리스크

- 화면의 금액·비율·일정·상태·설명·Curve 좌표는 모두 mock fixture 값이다.
  금융 계산, 실제 환전, 거래 실행, 계획 생성·저장과 실제 AI 호출은 포함하지 않는다.
- sessionStorage의 목표별 확인 표시는 연출 길이만 바꾼다. 적용 시나리오와 기록
  상태는 화면 로컬 상태이며 새로고침 뒤 서버 상태처럼 복원하지 않는다.
- 실제 API 계약이 없는 비데모 모드에서는 빈 상태를 표시한다.
- 배포 환경에서 `/route` 직접 접근을 지원하려면 정적 호스트의 SPA fallback이
  필요하다. Vite 개발 서버에서는 fallback이 동작한다.
- 안전·유연 구간, 회차 정책과 상황별 응답 생성 규칙은 기획 확정 뒤 fixture와
  API 타입을 교체해야 한다.
